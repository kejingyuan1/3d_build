## 1. 总体架构

### 1.1 部署形态


### 1.2 分层原则

| 层 | 职责 | 依赖方向 | 禁则 |
|---|---|---|---|
| 渲染层 (three) | 显示世界、相机、后处理 | 只读游戏状态 + SyncLayer 插值结果 | 不得持有游戏状态、不得直接改玩法数据 |
| 物理层 (rapier) | 碰撞、刚体模拟、查询 | 由游戏逻辑驱动 | 不得被渲染层直接操作 |
| 游戏逻辑层 | 状态机、生长、AI、存档 | 只依赖纯数据模块 | 不 import three / rapier 具体类型（经接口） |
| 同步层 | 物理→渲染变换回写 | 读物理、写渲染 | 不改变玩法逻辑 |

**关键约束**：Three.js 的 `Object3D` 只作为"视图"，游戏实体的权威数据（位置、生长度、健康值）存在逻辑层或物理层；渲染层永远不能是数据源。

## 2. Three.js + Rapier 集成架构

### 2.1 两个世界的关系

- **Rapier World** 是物理真相：所有可交互实体的位置/朝向/速度以物理世界为准。
- **Three.js Scene** 是视觉投影：每个游戏实体有一个渲染 `Object3D`。
- **同步层（SyncLayer）** 负责在物理步进后把 `RigidBody.translation()/rotation()` 写回对应 `Object3D`。

两者**不共享坐标系对象**，但使用**同一套坐标约定**（Y 轴向上，单位 = 1 米），因此变换可以直传：`mesh.position.set(rigidBody.translation().x, y, z)`，旋转用四元数直传，无额外换算。

### 2.2 步进策略（fixed timestep + 插值渲染）

| 项 | 决策 |
|---|---|
| 物理步长 | 固定 `dt = 1/60 s`（60Hz 模拟） |
| 渲染帧率 | 与显示刷新率一致（60/90/120Hz 自适应） |
| 累计器模式 | 渲染帧内累加 `elapsed`，`while (elapsed >= dt) { world.step(dt); elapsed -= dt; }` |
| 防螺旋 | 单帧最多 `maxSubSteps = 4`，超出丢弃剩余时间 |
| 渲染插值 | 保留上一物理状态与当前物理状态，渲染时按 `alpha = elapsed / dt` 做线性/四元数插值，消除抖动 |
| 锁步 | 单人模式为主，物理完全本地；多人（预留）时改为服务器权威 + 客户端预测 |

**决策记录 ADR-T1：固定步长 + 插值**
- 上下文：Web 游戏渲染帧率波动大，直接用 `requestAnimationFrame` 驱动物理会导致跳跃/穿透。
- 备选：A) 渲染帧驱动物理（实现简单、物理不稳定）；B) 固定步长无插值（物理稳、画面卡顿）；C) 固定步长 + 插值（本方案）。
- 决定：采用 C。
- 后果：实现复杂度略增（需双缓冲物理变换）；换取中端手机上稳定的物理表现。插值层必须与逻辑层解耦，避免逻辑读中间态。

**决策记录 ADR-T2：玩家刚体类型（P0 待 design 拍板）**
- 上下文：design 清单提议玩家 = dynamic capsule（r≈0.35m / 高≈1.7m / mass 80kg）；架构默认推荐 kinematic 角色控制器。
- 备选：A) Rapier `KinematicCharacterController` + capsule（推荐）：手感稳定、无抖动、天然处理斜坡/台阶，碰撞响应由控制器 sweep 提供；推挤类交互需额外实现。B) dynamic + mass 80kg：物理真实、可推挤/被推挤，但 Web 端需高 damping + CCD + auto-sleep + 速度钳制防抖动穿模。
- 决定：**暂未定**，倾向 A；若玩法核心含"物理推挤箱子/被动物顶开"则选 B（按 B 护栏实现）。该决策不影响资产管线，可延后。
- 后果：A 少写一层物理调试、手感好；B 更自然但调参成本高。两者都在 `engine/physics` 单点封装，切换成本可控。

### 2.3 刚体/碰撞体类型映射表

| Rapier 刚体类型 | 碰撞体类型 | 游戏对象 | 说明 |
|---|---|---|---|
| **fixed**（静态） | cuboid 组合 / convex hull / trimesh（低面） | 地形、建筑、围栏、静态装饰、道路 | 不可移动，碰撞体在加载时一次性构建 |
| **fixed** | heightfield | 大范围地表（设计清单确认：大地形 1 个 heightfield） | 内存友好、查询快；适合起伏地形 |
| **kinematic**（运动学） | capsule / cuboid | 围栏门段（kinematicPositionBased）、移动平台、门、推车、拾取中的道具 | 位置由逻辑直接设置，物理只提供碰撞查询与阻挡 |
| **dynamic**（动态） | ball / cuboid / capsule | 动物（鸡/牛/羊）、可拾取道具、果实、掉落物、投喂饲料、被推动物体 | 受重力与碰撞响应；AI 用 `setLinvel` 驱动；空闲自动睡眠 |
| **sensor**（触发器） | 按判定形状（ball/cuboid） | 交互判定：拾取范围、动物进食口、水面垂钓点 | `isSensor=true`，不参与碰撞响应，只发事件 |

**映射规则（写进控制清单）**：
1. 地形、建筑、静态装饰 → `fixed`，用**简化代理碰撞体**（box 组合），禁止直接拿渲染 mesh 建 trimesh（除非面数 < 500 且经批准）。大地形统一 heightfield。
2. 动物 → `dynamic` + capsule（对齐设计清单）。技术护栏：AI 用 `setLinvel` 驱动（不用 applyImpulse）、linear damping 1–2、空闲 `canSleep`、质量 30–50kg、最大速度钳制、动物间过滤组弱接触避免抖动堆叠。
3. 果实 / 道具 / 饲料 → `dynamic` + ball（或小 cuboid），空闲即睡眠；拾取时切 `kinematic` 或移除物理体（跟随手持），释放时恢复。
4. 交互判定（拾取范围、进食口、水面）→ `sensor` + 过滤组，只检测目标层（见 §2.5）。
5. 所有可交互实体必须注册到碰撞过滤组（§2.5），避免"果实与果实互相碰撞导致堆叠性能爆炸"。

### 2.4 事件与查询

- 使用 Rapier `CollisionEvent` / `ContactForceEvent` 处理拾取、投掷命中。
- 踩点/范围检测用 `world.intersectionWithShape` 或 `castRay`，避免为短暂交互创建常驻刚体。
- 玩家角色（P0，待 design 确认刚体类型，见 ADR-T2）：默认推荐 Rapier `KinematicCharacterController` + capsule（r≈0.35m / 高≈1.7m），手感稳定、不抖动、天然处理斜坡/台阶；若玩法确需物理推挤（推动箱子/被动物顶开），可改用 dynamic + mass 80kg，但必须加护栏（高 damping、CCD、auto-sleep、速度钳制），避免 Web 端抖动弹飞。该决策不影响资产管线，可延后拍板。

### 2.5 碰撞过滤组（Filter Group，5 层）

Rapier 用 32 位 membership/filter 位掩码，本项目固定分配 5 层（对齐设计清单第 4 章）：

| 层 | 用途 | 主要成员 | 碰撞策略 |
|---|---|---|---|
| 1 玩家 | 玩家角色 | 玩家 capsule | 与地面/静态/动物碰撞；不与掉落物层互相碰撞 |
| 2 动物 | 动物 | 鸡/牛/羊 capsule | 与地面/静态/玩家碰撞；动物之间弱接触或互不碰撞（防堆叠抖动） |
| 3 掉落物 | 鸡蛋/牛奶/饲料/果实 | 小型 ball/cuboid | 只与地面容器/静态碰撞，互不碰撞（防堆积性能爆炸） |
| 4 工具命中 | 投掷/命中判定 | 投掷物 Sensor 或 ray | 只检测目标层，避免误伤动物 |
| 5 交互 Sensor | 拾取/进食/水面判定 | 交互 Sensor | 只检测对应层（玩家层 / 掉落物层） |

规则：Solver 参与度按层控制；掉落物与工具命中默认不与其他动态刚体碰撞；动物层参与度受限（弱接触）。

## 3. 碰撞体与网格资产的关系

### 3.1 三种候选策略

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 碰撞体随模型自定义属性 | GLB 内嵌 userData / 自定义扩展（如 `extra.collider`）记录形状参数 | 一次建模处处一致；美术可控 | Web 工具链对 GLB 自定义扩展支持不成熟；程序化资产会重复冗余信息；维护成本高 |
| B. 运行时按类别规则生成（推荐） | 代码侧"类别 → 碰撞体模板"表：植物=树干 cylinder + 树冠 ball；建筑=box 组合；动物=capsule | 零额外资产体积；碰撞体永远低面数；与程序化生成参数天然一致 | 需要类别规则覆盖全部资产；特殊形状需例外 |
| C. 额外碰撞体占位对象 | 场景内放置带 `_collider` 前缀的不可见代理对象 | 完全灵活，可手调任意形状 | 场景文件变重；占位对象与渲染对象容易失配（漂移）；需要运行时对账 |

### 3.2 推荐方案（混合，主 B 辅 C）

**主策略 B（运行时按类别规则生成）+ 例外策略 C（占位对象）**。

理由：
1. 本项目的资产以**程序化生成**为主，生成器本就持有参数化几何（树干半径/高度、树冠半径、动物体型），直接由生成器元数据派生出碰撞体，信息零冗余。
2. 运行时生成可强制"渲染 mesh 永不用于物理"，碰撞体必然是简化代理，天然满足性能预算。
3. CC0 导入资产量大且来源混杂，逐个体检自定义属性不现实；按类别规则生成统一可控。
4. 对无法规则化的形状（河流弯道、特殊地形、自定义结构物），允许在资产/场景中放置 `_collider_*` 前缀的占位对象，导入时识别并转成代理碰撞体。

**落地方式（写进 asset-pipeline 元数据）**：
- 每个资产在 `manifest.json` 的 `collision` 字段声明碰撞体配置（类别 + 参数或 `placeholder` 引用），运行时读取 manifest 构建碰撞体，**不读 GLB 内嵌碰撞信息**。
- 例外占位对象命名规范：`_collider_<shape>_<index>`，如 `_collider_cuboid_00`、`_collider_cylinder_00`。

### 3.3 碰撞体参数建议值（写进控制清单）

| 形状 | 用途 | 建议参数 |
|---|---|---|
| cuboid | 建筑/围栏/箱体 | 按包围盒缩 5% 内缩，避免贴脸穿模 |
| cylinder | 树干/柱 | 半径 = 树干半径 × 1.0，高 = 树干高 |
| ball | 果实/道具/树冠 | 半径 = 视觉半径 × 0.85 |
| capsule | 角色/动物 | 半径 = 体宽/2 × 0.9，高 = 身高 − 2×半径 |
| trimesh（仅特批） | 地形/不规则大物 | 顶点数 ≤ 2000，禁止带材质三角形 |

## 4. 性能预算

目标设备分级：
- **T1 桌面浏览器**：独立显卡 / 1080p+，帧率目标 60fps。
- **T2 中端手机**：近年中端 SoC（如骁龙 7 系 / 天玑 8000 级），1080p 或以下，帧率目标 30fps 保底、60fps 期望。

### 4.1 统一预算表

| 指标 | T2 中端手机 | T1 桌面 | 备注 |
|---|---|---|---|
| 同屏可见对象数 | ≤ 300 | ≤ 1000 | 含静态实例化对象 |
| 动态刚体（dynamic）数 | ≤ 60 | ≤ 200 | 动物+掉落物+饲料合计（对齐设计清单 ≤60）；空闲即睡眠 |
| 物理碰撞体总数 | ≤ 500 | ≤ 1500 | 静态 + 动态合计 |
| Draw Calls | ≤ 150 | ≤ 350 | 静态合并 + InstancedMesh |
| 同屏三角面数 | ≤ 300k | ≤ 1M | LOD 切换兜底 |
| 单资产 LOD0 面数 | 植物 ≤ 500 / 动物 ≤ 3k | 植物 ≤ 2k / 动物 ≤ 8k | 见 asset-pipeline |
| 纹理显存占用（总） | ≤ 128MB | ≤ 512MB | 强制 KTX2/Basis 压缩 |
| 单纹理最大 | 1024×1024 | 2048×2048 | 特批除外 |
| 内存（JS heap + 资产） | ≤ 256MB | ≤ 1GB | |
| 帧耗时 | ≤ 33ms（30fps） | ≤ 16.7ms（60fps） | 渲染 + 物理 + 逻辑合计 |

### 4.2 优化手段（第一批内置，不做后补）

1. **静态合批 / InstancedMesh**：地形植被、围栏、重复建筑用 `InstancedMesh`，可合并同类 DrawCall。
2. **LOD**：每个资产提供 LOD0/LOD1/LOD2（或距离剔除），切换阈值由 manifest 配置。
3. **视锥 + 距离剔除**：渲染层剔除；物理层用 `RigidBodyActivation` 让远处刚体休眠。
4. **纹理压缩**：全部贴图走 KTX2/Basis（UASTC），mipmap 完整。
5. **DRACO/meshopt 压缩**：GLB 传输压缩，加载后解码。
6. **帧预算探针**：开发期 HUD 显示 ms 分解（渲染/物理/逻辑），CI 冒烟基准记录回归。

### 4.3 渲染管线支持项（对美术规格的确认）

| 支持项 | 状态 | 说明 |
|---|---|---|
| gradientMap 卡通明暗（MeshToonMaterial + gradientMap 3 阶） | ✅ 支持 | Three.js `MeshToonMaterial` + `gradientMap`（3 阶梯度贴图）原生支持，显存开销可忽略。约定：GLB 材质不内嵌扩展，由 manifest `materialMode: "toon"|"standard"` 字段决定加载器映射（与碰撞策略一致，见 asset-pipeline §4.1） |
| InstancedMesh 批量植被/围栏 | ✅ 支持 | 已在 §4.1 预算内：T2 DrawCalls ≤150 含 InstancedMesh 合并；单批实例建议 ≤ 2048（超出拆批）；支持 per-instance 随机缩放/旋转/颜色 |
| KTX2/Basis 纹理压缩 | ✅ 支持 | 已纳入 asset-pipeline §3.1/§3.2：gltf-transform 离线转 KTX2（UASTC）+ mipmap；运行时 `THREE.KTX2Loader` 解码；安卓兼容 fallback 见 §7 |

**取舍说明**：MeshToonMaterial 不支持复杂 PBR 特性，与卡通 Stylized 目标一致，无损失；若个别资产需标准 PBR（如水面/金属），`materialMode: "standard"` 走 MeshStandardMaterial，两类可同场景共存。gradientMap 梯度贴图由 art 侧统一提供（建议 3 阶，含环境色阶），加载器全局注入。

## 5. 后端服务器职责（第一批范围）

### 5.1 职责边界

| 职责 | 第一批 | 说明 |
|---|---|---|
| 静态资源托管（CDN） | ✅ | `.glb/.png/.ktx2/.json` 全部走 CDN，长缓存 + hash 文件名 |
| 资产版本管理 | ✅ | `manifest.json` 版本化，客户端拉最新清单增量加载 |
| 存档 API | ✅（要点） | REST/JSON，服务器权威 |
| 多人同步 | ⬜（预留） | WebSocket 通道设计预留，不在第一批实现 |
| 账户系统 | ⬜（最小可行） | 可用设备 ID + 可选昵称，不做复杂账号 |

### 5.2 资产版本管理

- 每个资产文件名带内容 hash：`assets/plants/carrot_leafy_a1b2c3.glb`。
- `manifest.json` 声明 `schemaVersion`、`assets` 数组、每个资产 `hash/version`。
- 客户端启动拉 manifest，比对本地缓存（IndexedDB / Cache Storage），**懒加载**用到的资产，其余按 `loadPriority` 后台预取。
- 服务器发布流程：打包 → 生成新 hash 清单 → 原子切换 manifest 指针 → 旧 hash 资产可留缓存。

### 5.3 存档 API 设计要点（不展开实现）

- **形态**：`POST /api/save`、`GET /api/load`、`GET /api/player/<id>`（预留）。
- **权威**：服务器为存档唯一真相，客户端只提交"增量操作事件"或整份压缩 JSON（第一批整份 JSON，字段版本化 `saveVersion`）。
- **防篡改**：服务端对存档 JSON 做 HMAC 签名；客户端上传校验字段白名单；金额/时长等关键数值服务端重算（防离线修改）。
- **节流**：写档频率限制（如 30s 一次自动存档 + 手动存档），防刷。
- **错误处理**：存档冲突（多端同时写）用 `lastWriteAt` 时间戳 + 版本号，冲突时服务端返回合并建议。
- **容量**：单存档目标 ≤ 200KB（压缩后），超出部分（如布局快照）走独立资源表。

## 6. 技术栈清单

### 6.1 核心依赖

| 依赖 | 用途 | 建议版本 | 版本策略 |
|---|---|---|---|
| `three` | 渲染引擎 | ^0.170（锁定 minor） | 锁 minor，升级走评审 |
| `@dimforge/rapier3d-compat` | 物理（Rust→WASM） | ^0.14（锁定 minor） | 锁 minor；`-compat` 变体兼容 CommonJS/打包器 |
| `vite` | 构建/开发服务器 | ^6 | 跟随 LTS |
| `typescript` | 类型 | ^5.5 | 锁 minor |
| `@gltf-transform/*` | 离线 GLB 优化管线 | latest（CI 外使用） | 离线工具，不进入运行时依赖 |
| `ktx2` / basis 编码工具 | 纹理压缩 | 随 gltf-transform | 离线 |

**版本策略总则**：
1. `package-lock.json` 提交入库，保证可复现构建。
2. 运行时依赖**锁 minor**，patch 自动接受；major 升级必须过架构评审（尤其 rapier 的 WASM 二进制变更）。
3. CI 每周跑一次 `npm outdated` 生成升级建议，人工决定。
4. 引擎版本超出训练数据时标记知识缺口（见 §7）。

### 6.2 构建与工程

- 打包目标：`es2020`，产物 `dist/` 纯静态，可直接扔 CDN。
- 代码组织（建议）：`src/engine/`（three/rapier 封装）、`src/game/`（逻辑）、`src/sync/`（同步层）、`src/assets/`（manifest + loader）、`src/ui/`。
- 质量门：`tsc --noEmit` + `eslint` + 冒烟测试在 CI 必过；物理回归用 Rapier 确定性测试（同种子同输入必须同输出）。

## 7. 风险与知识缺口登记

| 风险/缺口 | 等级 | 缓解 |
|---|---|---|
| rapier3d-compat 新版本 API 变化 | 中 | 锁 minor + CI 编译期检查；关键 API 封装在 `engine/physics` 单点 |

## 8. 控制清单（一页规则，程序员可直接执行）

1. 坐标系：Y 轴向上，1 单位 = 1 米，Z 轴为角色前向。任何资产/场景违反此约定即打回。
2. 物理：可交互实体必须经 `engine/physics` 接口创建；禁止直接 new Rapier 对象散落业务代码。
3. 碰撞体：渲染 mesh 永不直接进物理；一律用简化代理（cuboid/ball/capsule/cylinder），trimesh 需特批。
4. 刚体类型：地形/建筑/装饰=fixed（大地形 heightfield）；动物/道具/果实/饲料=dynamic（空闲睡眠）；围栏门段/平台/拾取中道具=kinematic；交互判定=sensor。不许混用。
5. 过滤组：5 层固定分配（玩家/动物/掉落物/工具命中/交互 Sensor，见 §2.5）；掉落物层互不碰撞；工具命中只检测目标层。
6. 步进：固定 1/60s，累计器 + 插值渲染；禁止在 rAF 回调里直接 `world.step(dt)`。
7. 数据流：渲染层只读；游戏逻辑层不 import three/rapier 具体类型（经接口）。
8. 资产：文件名带 hash；manifest 是碰撞体配置唯一来源；不读 GLB 内嵌碰撞信息。
9. 性能：超过预算表（§4.1）即优化，不允许上线带超预算指标。
10. 存档：服务器权威，客户端不信任；关键数值服务端重算。
11. 版本：运行时依赖锁 minor，lockfile 入库，major 升级走评审。
